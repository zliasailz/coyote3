# Coyote3 Setup — Clean Sequential Install (as of 2026-09-12)

A start-to-finish install sequence for standing up Coyote3 on a **new**
machine, distilled from the pilot deployment on `saile` — every command
below already has the mistakes/dead-ends from that pilot ironed out. Follow
it top to bottom on a fresh host and you should reach a fully running,
verified instance without hitting any of them again.

This is the "just run it" version. For *why* each step is the way it is,
or if something here doesn't match what you see, the full story is in:
- `docs/deployment_notes_saile.md` — chronological pilot journal (mistakes
  included, with how they were found and fixed)
- `docs/docker_issue.md` — the one host-level issue big enough to warrant
  its own document (Step 0 below)
- `docs/internal/known_issues.md` — upstream Coyote3 bugs and their fixes
- `docs/internal/production_deployment_checklist.md` — everything this
  pilot-style setup does **not** cover (TLS, LDAP, SMTP, KB licensing,
  backups, real clinical validation) — read that before calling any
  install "production"

Replace every `<angle-bracket>` placeholder with a real value for your host.

---

## Step 0 — Host prerequisite check (do this first, always)

```bash
docker info | grep -i "Docker Root Dir"
```

If the path is under `/var/snap/docker/...`, **stop** — this host has
Docker installed via the snap package, whose AppArmor confinement silently
blocks `docker stop`/`kill`/`restart` on every container. Install
`docker-ce` from Docker's official apt/yum repo instead (see
`docs/docker_issue.md` for the full fix if a snap install is already
present and has containers on it). Confirm before continuing:

```bash
docker info | grep -iE "Docker Root Dir|Operating System"   # expect /var/lib/docker
docker compose version                                       # confirm v2 plugin present
```

## Step 1 — Get the code

```bash
git clone <your-fork-url> coyote3
cd coyote3
git checkout center/main
```

All scripts in `scripts/` are committed without the executable bit (an
upstream packaging quirk). Always invoke them as `bash scripts/foo.sh ...`,
never `./scripts/foo.sh` — that will fail with "Permission denied".

## Step 2 — Host storage layout

Pick a data root **outside** the repo (keeps ingest/runtime data separate
from application code):

```bash
export COYOTE3_DATA_ROOT=<e.g. /opt/coyote3_data or /home/<user>/coyote3_data>

mkdir -p "$COYOTE3_DATA_ROOT"/{app-data,logs,mongo/data,mongo/backups}

openssl rand -base64 756 > "$COYOTE3_DATA_ROOT/mongo/keyfile"
chmod 600 "$COYOTE3_DATA_ROOT/mongo/keyfile"
```

## Step 3 — Check for port conflicts before writing the env file

```bash
ss -ltnp 2>/dev/null | grep -E ":27017|:6379|:5815"   # Mongo / Redis / default app port
```

If `27017` is already bound by something unrelated, pick a different
`COYOTE3_MONGO_PORT` in Step 4 (this happened on the pilot host due to an
unrelated pre-existing stack) rather than fighting over the port.

## Step 4 — Environment file

```bash
cp deploy/env/example.env .coyote3_env
```

Edit `.coyote3_env` and set, at minimum:

```bash
ENV_NAME=staging          # ONLY development/production/testing/staging are valid here.
                           # This is a different setting from a sample's own "environment"
                           # field (which additionally allows "validation") — don't confuse them.

COYOTE3_DB=coyote3_<env>
IDENTITY_DB=coyote3_identity_<env>
KNOWLEDGEBASE_DB=coyote3_kb_<env>
BAM_DB=bam_<env>

COYOTE3_MONGO_PORT=27017  # or an alternate free port from Step 3

COYOTE3_UID=<your-uid>    # `id -u`
COYOTE3_GID=<your-gid>    # `id -g`
MONGO_UID=<your-uid>
MONGO_GID=<your-gid>

COYOTE3_DATA_HOST_ROOT="$COYOTE3_DATA_ROOT/app-data"
COYOTE3_LOGS_HOST_ROOT="$COYOTE3_DATA_ROOT/logs"
COYOTE3_MONGO_DATA_HOST_ROOT="$COYOTE3_DATA_ROOT/mongo/data"
COYOTE3_MONGO_KEYFILE_HOST_PATH="$COYOTE3_DATA_ROOT/mongo/keyfile"
COYOTE3_MONGO_BACKUP_HOST_ROOT="$COYOTE3_DATA_ROOT/mongo/backups"

COYOTE3_APP_NETWORK=coyote3-app-net
PUBLIC_BASE_URL=http://<host-or-ip>:<port>     # use https in a real deployment
COYOTE3_NGINX_PUBLIC_SCHEME=http               # https in a real deployment
AUTHENTICATION_PROVIDERS=local
ORGANIZATION_NAME="<Your Center Name>"
```

Generate secrets (every one of these must be freshly generated per
deployment — never copy a secret between environments):

```bash
python3 -c "import secrets; print(secrets.token_hex(32))"   # SECRET_KEY
python3 -c "import secrets; print(secrets.token_hex(32))"   # INTERNAL_API_TOKEN
python3 -c "import secrets; print(secrets.token_hex(32))"   # PASSWORD_TOKEN_SALT
openssl rand -hex 32                                        # REDIS_PASSWORD (must be >=64 hex chars)
openssl rand -hex 24                                        # MONGO_ROOT_PASSWORD
openssl rand -hex 24                                        # MONGO_APP_PASSWORD
```

Paste each into the matching `.coyote3_env` key, then validate:

```bash
bash scripts/validate_env_secrets.sh --env-file .coyote3_env
```

Fix anything it flags before continuing (a too-short `REDIS_PASSWORD` from
`openssl rand -hex 24` instead of `-hex 32` is the most common miss).

## Step 5 — Docker network

```bash
docker network create "${COYOTE3_APP_NETWORK:-coyote3-app-net}"
```

## Step 6 — Bring up MongoDB

```bash
bash scripts/compose-with-version.sh \
  -f deploy/compose/docker-compose.mongo.yml \
  --env-file .coyote3_env --profile mongo up -d

docker compose -f deploy/compose/docker-compose.mongo.yml ps
```

Wait for `mongo` to report healthy and `mongo_init` to exit 0 (it
initializes the replica set and creates the app user, then exits — that's
expected, not a crash).

## Step 7 — Bootstrap RBAC and reference data

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Run bootstrap **once**, against the fresh empty databases:

```bash
python3 scripts/bootstrap_database.py --with-demo-center \
  --mongo-uri "mongodb://coyote3_app:<MONGO_APP_PASSWORD>@127.0.0.1:<COYOTE3_MONGO_PORT>/?directConnection=true" \
  --superuser-email <admin-email> \
  --sysadmin-email <different-sysadmin-email>
```

Notes:
- Use `directConnection=true`, **not** `replicaSet=...`, when connecting
  from the host shell — the replica set advertises its Docker-internal
  hostname, which the host can't resolve. The application containers
  connect correctly with the full `replicaSet=` URI on their own; this
  only matters for this one-off host-side bootstrap run.
- Superuser and sysadmin **must** use distinct email addresses — the
  script refuses a collision.
- Drop `--with-demo-center` for a real production database; use it only
  for an initial smoke test, and never re-run bootstrap against a
  database that already has real data.
- Save the printed temporary passwords somewhere safe — they're shown
  once and forced to change on first login.

## Step 8 — Bring up the full application stack

```bash
bash scripts/compose-with-version.sh \
  -f deploy/compose/docker-compose.yml \
  --env-file .coyote3_env up -d --build

bash scripts/center_preflight.sh
```

If `center_preflight.sh` complains about a missing `COYOTE3_IMAGE_TAG`,
export it manually first (it doesn't derive the tag the way
`compose-with-version.sh` does):

```bash
export COYOTE3_IMAGE_TAG="$(python3 api/version.py)-<env-short-name>"   # e.g. 4.0.0-stage
```

Verify:

```bash
docker compose -f deploy/compose/docker-compose.yml --env-file .coyote3_env ps
curl -s http://127.0.0.1:<COYOTE3_PORT>/api/v1/health   # expect {"status":"ok"}
```

## Step 9 — Firewall (only if accessed from another machine)

```bash
sudo ufw allow from <your-subnet e.g. 192.168.0.0/24> to any port <COYOTE3_PORT> proto tcp
```

Nothing about Coyote3 itself opens firewall ports — this is always a
manual step, and easy to forget if you only test from `localhost` on the
server itself.

## Step 10 — First login

Open `http://<host>:<COYOTE3_PORT>` in an actual browser (not just `curl`)
and log in with the superuser email/temporary password from Step 7.
Complete the forced password change.

## Step 11 — Center-specific configuration

- `api/config/center/contact.toml` — set your real organization name and
  support contacts.
- `ORGANIZATION_NAME` in `.coyote3_env` flows automatically into the UI
  wordmark — no code change needed.
- Any change under `api/config/` is baked into the API image at build
  time — it needs `up -d --build` plus a real container recreate to take
  effect. There is no live-reload for these.
- Create real operational RBAC roles via `POST /api/v1/roles` (or the
  admin UI). If scripting this directly: the request body must be wrapped
  as `{"form_data": {...fields...}}`, not flat JSON — this is the generic
  admin-resource form contract, not specific to roles.

## Step 12 — Ingest smoke test (optional but recommended)

Validate a demo manifest end-to-end before pointing a real pipeline at
this instance:

```bash
python3 scripts/validate_ingest_spec.py demo_data/ingest/generic_case_control.yaml
```

Then either drop it (plus its referenced files) into the watched ingest
directory, or submit it via the token-authenticated API
(`POST /api/v1/internal/ingest/sample-bundle/upload`) — see
`docs/api/sample_yaml.md` for the manifest contract and
`docs/internal/production_deployment_checklist.md` §7 for choosing
between the two transports.

## That's a working instance. Before calling it "production":

This sequence gets you a correctly running Coyote3 instance using local
accounts, plain HTTP, and placeholder center configuration — appropriate
for a pilot/validation box, not a real deployment. Read
`docs/internal/production_deployment_checklist.md` in full before going
further — it covers TLS, LDAP, SMTP, knowledgebase licensing, backup
rehearsal, and the real clinical validation study, none of which this
document attempts.
