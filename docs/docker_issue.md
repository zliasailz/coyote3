# Docker Issue: `stop`/`kill`/`restart` fail with "permission denied" on a host with the Docker *snap* package installed

Standalone technical write-up of a host-level Docker bug found and fixed
during the Coyote3 pilot deployment. This is **not** a Coyote3 bug — it can
affect any container, from any project, on an affected host. Written up
separately from `docs/deployment_notes_saile.md` (the chronological pilot
journal) because it's general-purpose and worth keeping even if the rest of
that journal becomes irrelevant. See `deployment_notes_saile.md` §16 for
the full chronological account of diagnosing and fixing this during the
pilot, including all commands run.

## Summary

If a host has Docker installed via `snap install docker` (Ubuntu's snap
store package), every container gets Docker's standard `docker-default`
AppArmor profile — but that profile has no rule allowing it to **receive**
a stop/kill signal from a peer with the snap's AppArmor confinement label
(`snap.docker.dockerd`). The kernel blocks the signal outright. The result:
`docker stop`, `docker kill`, `docker restart`, and anything that depends
on them (`docker compose up` recreating a running container, `docker rm`
without `-f`, etc.) all fail with a generic-looking
`Error response from daemon: cannot stop container: ...: permission denied`
— for every container, regardless of who created it or how, and regardless
of which user or terminal issues the command. A direct OS-level
`sudo kill -9 <pid>` still works, because it bypasses Docker's own signal
path entirely.

**Fix**: stop using the Docker snap. If a non-snap `docker-ce` install is
already present on the host (common — many hosts end up with both,
whichever was installed second usually loses the socket race silently),
cut over to it. Otherwise, install `docker-ce` from Docker's official apt/
yum repository and remove the snap.

## Symptom

```
$ docker restart my-container
Error response from daemon: cannot stop container: <id>: permission denied
```

Same error for `docker stop`, `docker kill`, and any `docker compose up`
that needs to recreate an already-running container. Notably:

- `docker build`, `docker create`, `docker exec` (into an already-running
  container), `docker rename`, `docker update`, `docker rm` (on an
  already-stopped container), and all read-only inspection commands work
  completely normally — **only the "stop/kill a running container" family
  is affected.**
- It reproduces on a disposable, freshly-created, completely unrelated
  container — it is not specific to any particular image, compose project,
  or however the container was originally started.
- It reproduces identically for every user/terminal on the host, not just
  one particular shell or session.
- `sudo kill -9 $(docker inspect -f '{{.State.Pid}}' my-container)` works
  as a manual escape hatch — this is often the first workaround people
  find, and it's actually a useful diagnostic clue (see root cause).

## Root cause

Confirmed via the kernel's AppArmor audit log:

```bash
journalctl -k --no-pager | grep -i apparmor | grep -iE "denied|signal"
```

```
apparmor="DENIED" operation="signal" class="signal" profile="docker-default"
requested_mask="receive" denied_mask="receive" signal=term
peer="snap.docker.dockerd"
```

Reading this precisely: the **container's own process** (confined under
AppArmor profile `docker-default`, the standard profile Docker attaches to
every container) is refusing to **receive** a `SIGTERM`/`SIGKILL` signal
sent by a peer process labeled `snap.docker.dockerd`.

`snap.docker.dockerd` is the AppArmor confinement label snapd generates for
the Docker daemon when Docker is installed via `snap install docker` — the
snap store version, as opposed to the `docker-ce` package from Docker's own
apt/yum repository. Snap packages run under strict AppArmor confinement by
design. The `docker-default` container profile, however, is generated by
upstream Docker/Moby itself and predates (and is unaware of) the
possibility that the daemon signaling the container might itself be
snap-confined — it has an explicit rule permitting signals from
`unconfined` peers (ordinary, non-snap processes), but no rule for a peer
labeled `snap.docker.dockerd`. AppArmor's `signal` mediation is enforced
independently of standard Linux capabilities: the daemon runs as root with
`CAP_KILL`, which would normally be sufficient to send any signal, but
AppArmor's kernel LSM hook vetoes it before that even comes into play. This
is exactly why `sudo kill -9` (issued from an ordinary, unconfined
interactive shell) always succeeds where `docker stop` does not.

### Why this can be confusing to diagnose

1. **Two daemons can coexist on one host**, each listening for
   `/run/docker.sock` (the canonical path `/var/run/docker.sock` normally
   symlinks to). If both the snap and a `docker-ce` install are present
   and enabled, whichever bound the socket path first (typically whichever
   started earlier at boot) silently "wins," and the CLI talks to it —
   even if `systemctl status docker.service` reports the other one as
   perfectly healthy and active. Don't trust systemd unit status alone to
   determine which daemon is actually serving requests.
2. **`docker info`'s "Operating System" field can mislead.** A
   snap-confined `dockerd` reports the OS of its own snap confinement base
   (e.g. `Ubuntu Core 24`), not the real host OS — even on an ordinary
   Ubuntu Server install with a normal, mutable root filesystem and full
   `apt`/`dpkg`. Don't conclude the host is an immutable, snap-only OS
   from this field alone; check `/etc/os-release` directly.
3. **`docker info`'s "Docker Root Dir" is the reliable tell.** A path
   under `/var/snap/docker/common/var-lib-docker` means the snap daemon is
   the one actually answering; `/var/lib/docker` means it's the standard
   package.

## Fix

### If `docker-ce` is already installed on the host (check first)

```bash
dpkg -l | grep -E "docker-ce|containerd.io"
systemctl status docker.service docker.socket
```

If present, this is a pure cutover — no package installation needed:

1. **Stop anything currently running under the snap daemon first**, since
   containers created there won't be visible to the other daemon (they use
   separate data-roots). For each running container, a normal
   `docker stop`/`docker compose down` will hit this exact bug — force-kill
   the process directly instead, then remove the now-exited container
   normally:
   ```bash
   sudo kill -9 $(docker inspect -f '{{.State.Pid}}' <container>)
   docker compose down   # now succeeds, since nothing is "running" to signal
   ```
2. **Disable the snap daemon** so it can't win the socket race again (on
   this boot or a future one):
   ```bash
   sudo systemctl stop snap.docker.dockerd.service
   sudo systemctl disable snap.docker.dockerd.service
   ```
3. **Let the standard daemon reclaim the socket cleanly:**
   ```bash
   sudo systemctl restart docker.socket docker.service
   docker info | grep -iE "Docker Root Dir|Operating System"
   # expect /var/lib/docker and the real host OS string
   ```
4. **Migrate any Docker-managed named volumes** (bind-mounted host paths
   need no migration — only volumes created with `docker volume create`,
   including ones Compose creates implicitly, live under the daemon's own
   data-root and won't be visible to the other daemon):
   ```bash
   sudo mv /var/snap/docker/common/var-lib-docker/volumes/<name> /var/lib/docker/volumes/
   docker volume create <name>   # registers it; reuses the existing data in place, does not wipe it
   ```
   Both data-roots are typically on the same filesystem, so `mv` is
   instant and needs no extra disk space. **Registration matters**: modern
   Docker's `local` volume driver tracks known volumes in an internal
   metadata store, not by scanning the filesystem — moving the raw
   directory alone is not sufficient for `docker volume ls` to see it.
5. **Recreate any external Docker networks** referenced by your compose
   files (`docker network create <name>`) — networks aren't shared between
   daemons either.
6. **Bring everything back up** under the now-active standard daemon.
   Watch for **orphaned container processes**: `containerd-shim` processes
   are deliberately designed to survive a daemon stop, so a container that
   could never be cleanly `docker stop`ped due to this exact bug may still
   have a live process on the host even after its container object is
   gone from `docker ps`. This can cause a freshly recreated container
   (e.g. a database) to fail to start with a data-directory lock conflict.
   Find and clear it with:
   ```bash
   ps aux | grep <process-name>   # e.g. mongod, postgres, etc.
   sudo kill -9 <pid>
   ```
7. **Verify the actual fix**, not just that containers are running:
   ```bash
   docker restart <any-running-container>   # should exit 0 and actually restart
   ```
8. **Once confident everything is stable**, remove the snap entirely to
   eliminate the ambiguity permanently:
   ```bash
   sudo snap remove docker
   ```
   (snapd takes an automatic data snapshot before removing, as a safety
   net.)

### If `docker-ce` is not installed at all

Install it from Docker's official repository (see
<https://docs.docker.com/engine/install/> for your distribution), then
follow steps 1–8 above.

## Prevention

On any new host, before deploying anything, check which Docker package is
installed:

```bash
docker info | grep -i "Docker Root Dir"
```

A path under `/var/snap/docker/...` means this bug is latent on that host
and will surface the first time anything needs a container restart or
redeploy. Install `docker-ce` from the start instead of `snap install
docker`, and this never comes up at all — it's specifically a property of
the snap package's AppArmor confinement, not something particular to any
one application or compose project.
