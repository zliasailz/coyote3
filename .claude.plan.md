# Coyote3 Pilot Deployment — Phase Plan (this machine: "saile")

Concrete, task-level plan for standing up a full Coyote3 instance on this
machine as a validation/pilot before real server/cloud deployment. This is
the execution plan for Phases 2–9 of the broader adoption roadmap
(`~/.claude/plans/here-is-the-codebase-enchanted-hartmanis.md`), scoped to
this specific box. Narrative/how-to writeup lives in
`docs/deployment_notes_saile.md` and is kept current alongside this list.

Execution mode: I prepare each phase's config/commands, then ask before
running anything with live side effects (starting containers, bootstrapping
databases, etc.).

## Decisions locked in so far

- Base architecture: `api` branch (v4.0.0 FastAPI/React rewrite), not
  `master` (v3.1.x Flask).
- Fork: `https://github.com/zliasailz/coyote3.git` (`origin`); SMD Lund is
  `upstream`. Work happens on `center/main`.
- This machine is a **validation/pilot box**, not final production.
- MongoDB: single shared `mongod` container (`docker-compose.mongo.yml`,
  `mongo` profile only).
- Auth: local accounts only (LDAP deferred).
- Network: internal LAN, plain HTTP (`http://192.168.0.30:6801`).
- Pilot/ingest data lives entirely outside the repo, under
  `/home/saile/develop/coyote_data/` (separate from
  `/home/saile/develop/coyote3/`).
- `ENV_NAME=staging` (deployment-level; only dev/prod/test/stage are valid —
  `validation` is a *sample-level* field instead, a different concept; see
  deployment notes for how this was caught).

## Phase 7.5 — Host-level Docker fix (unplanned, inserted before Phase 8)

- [x] Root-caused the `docker stop`/`kill`/`restart` "permission denied"
  seen throughout Phase 7: not an assistant-sandbox restriction (it
  reproduced identically from the operator's own terminal on the
  unrelated pre-existing `omixia` stack) — a real, host-wide bug. Kernel
  audit log (`journalctl -k | grep apparmor`) showed the `docker` *snap*
  package's AppArmor confinement (`snap.docker.dockerd`) being denied
  permission to signal containers under the standard `docker-default`
  profile, which has no rule for that peer.
- [x] Fixed by cutting over to the `docker-ce` apt package that was
  already installed on the host but losing a socket race to the snap:
  disabled `snap.docker.dockerd.service`, restarted `docker.socket`/
  `docker.service`, migrated `omixia`'s 3 Docker-managed named volumes
  from the snap data-root to the new one (`sudo mv`, same filesystem),
  re-registered them with `docker volume create` (modern Docker's `local`
  driver needs explicit registration, not just files on disk), recreated
  the `coyote3-pilot-app-net` network, and brought both `omixia` and
  Coyote3 back up under the new daemon.
- [x] Hit and resolved one more artifact of the original bug: Coyote3's
  `mongo` container's process had survived as an orphan on the host
  (`containerd-shim` deliberately outlives a daemon stop) and was
  holding the data-directory lock, crash-looping the freshly recreated
  container — found via `ps aux | grep mongod`, force-killed the orphan,
  clean restart followed.
- [x] Verified the actual fix: `docker restart coyote3_prod-monitor-1`
  now succeeds (exit code 0) — the exact operation that failed
  throughout Phase 7. Full app re-confirmed healthy end-to-end.
- [x] This means Phase 7's contact.toml and BrandWordmark.tsx changes,
  previously build-ready but undeployed, are now actually live (deployed
  via the `up -d --build` run as part of this recovery) — **Phase 7 is
  now fully closed, not just source-ready.**
- [x] Deleted the now-unnecessary
  `docker-compose.snap-apparmor-workaround.yml` overlay (an earlier,
  narrower per-service workaround, superseded by the real host-level
  fix). Full write-up: `docs/deployment_notes_saile.md` §16. Updated
  KI-001's status in `known_issues.md` to reflect it's now verified via a
  real rebuild, not just a live patch.
- [ ] Optional follow-up, not blocking: `sudo snap remove docker` once
